please explain to me about each modules of "tun2socks",  what are their functions, how do they interact with each other ?

In xjasonlyu/tun2socks, the architecture is divided into modular packages that transform raw network packets into proxy-compatible streams. 

Core Modules and Functions

Module 	    Function
engine	    The orchestrator. It initializes the network stack, binds the TUN interface to the proxy handler, and manages the lifecycle of the tunnel.

tun	        Manages the Virtual Network Interface. It handles platform-specific logic to read/write raw IP packets from the OS (e.g., via VpnService on Android or Wintun on Windows).

proxy	    Implements Outbound Protocols. This contains the logic for SOCKS4, SOCKS5, HTTP, and Shadowsocks. It takes the reassembled streams and sends them to your remote server.

common	    Provides Shared Utilities. This includes logging, configuration parsing, and memory pooling (pool package) to keep the engine efficient under high load.

metadata	Extracts Connection Info. It parses IP packets to determine the destination IP and port, allowing the proxy module to know where to forward the traffic.
=================================================================

How do They Interact (The Packet Flow) ?

Ingress: The tun module reads a raw IP packet from the operating system's TUN device.

Stack Processing: The engine passes this packet into a user-space TCP/IP stack (powered by gVisor). This stack reassembles fragmented IP packets into a coherent TCP or UDP stream.

Routing: Once a stream is formed, the metadata package identifies its destination. The engine then looks up the appropriate proxy configuration.

Egress: The proxy module wraps the stream in the chosen protocol (e.g., SOCKS5) and sends it out through your physical network interface to the remote proxy server.

Return Path: Response data from the proxy server travels back through the stack, is turned back into IP packets by gVisor, and is written back to the tun device for the OS to receive. 

===============================================================
 Customization Impact

If you modify a specific module, here is what happens:

Modifying proxy: You can add support for new protocols (like Trojan or VLESS) without touching the network stack.

Modifying engine: You can change how connections are balanced or how DNS is intercepted.

Modifying tun: You can optimize how packets are buffered before being sent to the Go runtime, which is critical for performance on mobile devices.

a template for a Handshake function that handles encrypted headers for your new protocol


To implement a custom proxy protocol with an encrypted handshake in tun2socks, you will create a new package under proxy/ and implement the DialContext method. 
This method is responsible for establishing the underlying connection, performing the handshake, and returning a connection that tun2socks can use for data transfer. 

1. Protocol Implementation Template

Create proxy/myprotocol/proxy.go. This template demonstrates a handshake that sends an encrypted header (e.g., using AES-GCM) to a remote server before allowing traffic to pass. 

package myprotocol

import (
    "context"
    "crypto/aes"
    "crypto/cipher"
    "crypto/rand"
    "fmt"
    "io"
    "net"

    "://github.com"
)

type myProxy struct {
    addr string
    key  []byte // 32-byte key for AES-256
}

// DialContext establishes the connection and performs the handshake
func (p *myProxy) DialContext(ctx context.Context, network, addr string) (net.Conn, error) {
    // 1. Establish raw TCP connection to the proxy server
    conn, err := (&net.Dialer{}).DialContext(ctx, network, p.addr)
    if err != nil {
        return nil, fmt.Errorf("failed to dial proxy: %w", err)
    }

    // 2. Perform Encrypted Handshake
    if err := p.handshake(conn, addr); err != nil {
        conn.Close()
        return nil, fmt.Errorf("handshake failed: %w", err)
    }

    return conn, nil
}

func (p *myProxy) handshake(conn net.Conn, targetAddr string) error {
    // Example: Encrypt the target address as the "header"
    block, _ := aes.NewCipher(p.key)
    aesgcm, _ := cipher.NewGCM(block)

    nonce := make([]byte, aesgcm.NonceSize())
    io.ReadFull(rand.Reader, nonce)

    // Seal the target address (e.g., "google.com:443")
    ciphertext := aesgcm.Seal(nil, nonce, []byte(targetAddr), nil)

    // Write: [Nonce (12b)][Ciphertext (variable)]
    if _, err := conn.Write(append(nonce, ciphertext...)); err != nil {
        return err
    }
    
    // Optional: Wait for a 1-byte ACK from server to confirm decryption
    buf := make([]byte, 1)
    if _, err := io.ReadFull(conn, buf); err != nil || buf[0] != 0x01 {
        return fmt.Errorf("server rejected handshake")
    }
    return nil
}

what is "inter-packet arrival time"?

Inter-packet arrival time (IAT) refers to the precise time interval between two consecutive packets arriving at a network interface.

Think of it as the "rhythm" or "heartbeat" of a connection. Even if the data inside the packets is encrypted (TLS in TLS), the timing of when those packets are sent reveals a wealth of information about the underlying protocol.

Why IAT is a "Feature" for Probing?

Censors use IAT as a statistical fingerprint because encryption rarely hides the temporal behavior of an application. Here is why it’s dangerous for your setup:

Handshake Signatures: A standard TLS handshake has a very specific "ping-pong" rhythm (ClientHello → ServerHello → ChangeCipherSpec). 
If your proxy performs a local header check and then connects to a remote server, the delay between the "Server Noise" and the "Real Destination Data" might be much longer than a standard local TLS response. This "gap" identifies your server as a proxy.

Application Identification: Different apps have different rhythms.
    Web browsing looks like a burst of packets followed by silence.
    Video streaming looks like consistent, large bursts at fixed intervals.
    VPN/Tunneling often shows a "wrapper" rhythm that censors can distinguish from "native" HTTPS.

Active Probing Verification: When a censor replays a packet to your server, they measure how fast you respond. If your HeaderDecoder responds in 1ms but a real web server (that has to fetch a file from disk) responds in 30ms, the IAT difference flags you as an automated service (a proxy).

====================================================================

Recommendation for Pseudo-Traffic Length

To effectively hide, your length should be dynamic and MTU-aware.
    Minimum: ~128 bytes (to avoid being too small to be meaningful).
    Maximum: ~1400 bytes (stay below the standard 1500-byte MTU to avoid fragmentation).
    The "Sweet Spot" Strategy: Don't just pick a static number. Use a Randomized Range (e.g., 200 to 800 bytes).

Advanced Recommendation:
If you want to be truly stealthy, mimic the size of a Common HTTP Response Header. 
Most "ServerHello" or initial HTTP responses are between 400 and 700 bytes. By making your noise fall within this range, your first "burst" from the server looks like a standard web server responding to a browser.

How to apply this in your Netty Server:
Generate a random length between 400 and 700.
Generate bytes of pseudo-random data.
Inject a randomized delay (e.g., 10ms–50ms) before writing the noise to the channel. This mimics the time a real server would take to "think" or "process" a request.

============================================
How to Generate "Low-Entropy" Noise in Netty

1. The "Static Buffer" approach (Best Performance)
    Pre-load a few "junk" files into memory—fragments of common library files (.dll, .so) or compressed public domain images (.jpg).
    Implementation: Keep a large ByteBuf (e.g., 64KB) of a compressed file.
    Usage: For each new connection, pick a random offset and a random length from this buffer to send.
    Result: The entropy matches that of real-world compressed data, and there is no CPU overhead for generation.

2. The "Dictionary-Based" approach (Best Mimicry)
    If you want to mimic a specific protocol (like a SOCKS5 response or a fake HTTP header), use a dictionary of common strings.
    Implementation: Build a buffer starting with a legitimate-looking header (e.g., HTTP/1.1 200 OK\r\nServer: nginx\r\n...).
    Usage: Fill the remaining "length" with a mix of alphanumeric characters rather than purely random bits.

3. The "XOR Masking" of Zeroes
    If you need to generate it on the fly, take a buffer of zeros and XOR it with a low-complexity repeating key.
    Why: This creates a repeating pattern that is mathematically "messy" but lacks the high-entropy signature of a strong cipher.

Critical Detail: The Client-Side Sink

On your client-side, the receiver must be able to differentiate between your "Noise" and the "Real Data" that follows immediately after.
My Recommendation: Use the Length-Prefixed approach you mentioned earlier.
Byte 0-1: Magic Number / Version.
Byte 2-3: Noise Length (N).
Bytes 4 to 4 + N
: The Noise itself.

Next Byte: The start of the real proxied stream.
The client reads the first few bytes, sees N, calls in.skipBytes(N), and then switches its internal state to "Transparent Proxy Mode."

netty implementation for client side 

To implement the client-side "sink," you need a Stateful Decoder. Since the pseudo-traffic only happens once at the beginning of the connection, 
the decoder should handle the noise and then remove itself from the pipeline to ensure zero overhead for the rest of the session.

Netty Client-Side "Noise Stripper"
This implementation assumes the Length-Prefixed approach: [Length Short (2 bytes)] + [N bytes of Noise].

public class NoiseStripperDecoder extends ByteToMessageDecoder {

    private enum State { READ_LENGTH, SKIP_NOISE }
    private State currentState = State.READ_LENGTH;
    private int noiseLength = -1;

    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        switch (currentState) {
            case READ_LENGTH:
                if (in.readableBytes() < 2) return; // Wait for the length field
                noiseLength = in.readUnsignedShort();
                currentState = State.SKIP_NOISE;
                // Fall through to skip immediately if data is available
            
            case SKIP_NOISE:
                if (in.readableBytes() < noiseLength) return; // Wait for full noise payload
                
                // Discard the noise bytes
                in.skipBytes(noiseLength);
                
                // Success! Now remove this handler so it doesn't process real data
                ctx.pipeline().remove(this);
                
                // If there's extra data already in the buffer (the real stream), 
                // fire a channelRead so the next handler gets it.
                if (in.isReadable()) {
                    out.add(in.readRetainedSlice(in.readableBytes()));
                }
                break;
        }
    }
}

Critical Considerations
    The "Length" obfuscation: If you always send the length as a plain Short (2 bytes), a censor might notice that every connection starts with a small integer. You can obfuscate this by XORing the length bytes with a pre-shared key (PSK) known by both the client and server.
    
    Zero-Length Guard: Ensure your server-side never sends a noise length of 0 unless your client code explicitly handles it, otherwise you might trigger an infinite loop or index error.
    
    Timeouts: If the server validates the header but the noise never arrives (due to a network drop), the client might hang in SKIP_NOISE. Add a ReadTimeoutHandler to the pipeline during this phase.

======================================================
To hide the length field, you want to avoid sending a "naked" integer (like 0x00 0xFF), as sensors look for fixed-offset patterns. XOR-obfuscation with a Pre-Shared Key (PSK) or a session-derived byte makes the length look like random garbage to an outsider.

1. The Strategy: Simple XOR Masking
Instead of sending the raw length L, you send L XOR K, where K is a key known only to your client and server.
    Server side: writeShort(noiseLength ^ 0xABCD)

    Client side: int actualLength = in.readUnsignedShort() ^ 0xABCD



2. Implementation in Netty

server side 

// Define a constant mask (or derive one from your handshake)
private static final int MASK = 0xAF32; 

private void sendObfuscatedNoise(ChannelHandlerContext ctx, int length) {
    ByteBuf buffer = ctx.alloc().buffer(2 + length);
    
    // Mask the length
    buffer.writeShort(length ^ MASK);
    
    // Append the "low-entropy" noise
    buffer.writeBytes(getJunkData(length));
    
    ctx.writeAndFlush(buffer);
}

In tun2socks, the MTU is a global setting applied to the TUN device itself, which handles both TCP and UDP traffic. 

1. Where to Set the MTU
You have three ways to define this, depending on how you run your project:

Command Line: Use the -mtu flag when starting the binary.

./tun2socks -device tun0 -proxy troad://... -mtu 1300


YAML Config: If you use a configuration file, add the mtu key:

device: tun0
proxy: troad://...
mtu: 1300

System Commands: You can also set it manually on the network interface after it is created:

Linux: sudo ip link set dev tun0 mtu 1300
macOS: sudo ifconfig utun123 mtu 1300 

2. Recommended Value for Troad (TLS + DTLS)
Because your protocol adds multiple layers of overhead, a standard MTU of 1500 will likely cause fragmentation

Suggested MTU: 1300 to 1350 bytes.

Why?:
TCP: tun2socks (via the gVisor stack) will automatically derive the TCP MSS from this MTU (usually MTU - 40 bytes), ensuring TCP segments fit.
UDP: Since UDP lacks MSS negotiation, a lower MTU on the TUN device forces the application to send smaller packets, preventing them from exceeding the DTLS + SOCKS header limits of your tunnel. 

3. MTU Calculation Breakdown
Layer	                Typical Overhead
Standard Ethernet	    1500 bytes (Limit)
DTLS Header	            ~13–25 bytes
Troad/SOCKS5 Header	    ~10–22 bytes
Safe Margin	            ~50+ bytes
Final Result	        ~1350 or lower

Pro Tip: If you see "Packet Too Big" errors or high latency in your logs, keep dropping the MTU by 20 bytes until the connection stabilizes.

A Note on TCP MSS
For TCP, tun2socks usually handles MSS clamping automatically based on the TUN interface MTU. However, since you are wrapping TCP in TLS, you have extra overhead. If you notice TCP connections hanging (common for HTTPS sites), it means the TLS-in-TCP segments are too large.
The fix: Always ensure the Global MTU (set via -mtu flag) matches or is slightly lower than your td.mtu query parameter.

Yes. Go is a statically linked language.

Minimally.

Idle: It won't save much CPU while the app is just sitting there, because those packages only consume CPU when they are actively handling a connection.
Startup: It will slightly speed up the initial app launch (warm-up time) because the init() functions for all those registered protocols won't need to execute.

To implement the protect() function, you must bridge the Go network stack to the Android VpnService. 
This is necessary because every outbound socket created by the Go engine must be "protected" to bypass the VPN and avoid an infinite routing loop. 
====================================
1. Create a "Protector" Interface in Go
In your troadengine package, define an interface that Go can use to call back into Android.

package troadengine

// SocketProtector is an interface for Android's VpnService.protect()
type SocketProtector interface {
	Protect(fd int) bool
}

var protector SocketProtector

// RegisterProtector is called from Kotlin to provide the VpnService instance
func RegisterProtector(p SocketProtector) {
	protector = p
}

======================================

2. Update Go Dial Logic
You must ensure that every time the Go engine creates a new outbound connection (TCP or UDP), 
it calls this protector. In many tun2socks implementations, this is done by setting a Control function on the net.Dialer.

import (
	"context"
	"net"
	"syscall"
)

func getDialer() *net.Dialer {
	return &net.Dialer{
		Control: func(network, address string, c syscall.RawConn) error {
			return c.Control(func(fd uintptr) {
				if protector != null {
					protector.Protect(int(fd))
				}
			})
		},
	}
}
